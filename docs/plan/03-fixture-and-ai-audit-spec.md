# Fixture, PoC and AI repair-plan audit specification

**Status:** proposal, 2026-11-20
**Serves:** MVP2 phases P1 (fixture + PoC) and P2 (AI audit gate)
**Owner:** M3 (fixture, corpus, verification), M4 (disassembly, prompt, audit), M1 (contract, review)

This document is deliberately concrete. It defines the first three MVP
deliverables: the vulnerable C program, the PoC and the correct inputs, and the
audit that decides whether the model can propose a usable repair before anyone
writes a patch.

## 1. The fixture

### 1.1 C source (build-only)

The source lives in `fixtures/stack-overflow-01/build/vuln.c` and is marked
**BUILD-ONLY**. No analysis or prompt code may read this directory. It is
committed only so the binary can be rebuilt and its provenance checked.

```c
#include <stdio.h>
#include <string.h>

__attribute__((noinline))
static void handle(char *input)
{
    char buf[32];
    strcpy(buf, input);   /* CWE-121: unbounded copy into a 32-byte stack buffer */
    puts(buf);
}

int main(int argc, char **argv)
{
    if (argc != 2) {
        fprintf(stderr, "usage: %s <input>\n", argv[0]);
        return 2;
    }
    handle(argv[1]);
    return 0;
}
```

Why this shape:

- `handle` is a separate, non-inlined function with a symbol, so the analysis and
  the AI can talk about one target without whole-program reasoning.
- `strcpy` is a real PLT call at `-O0` with `-fno-builtin`, so there is a single
  5-byte `call` site to redirect.
- `buf[32]` is small enough to overflow with a short PoC, and large enough that
  the 31/32 boundary is meaningful.
- `puts` gives an observable valid-path output without a format string.

### 1.2 Build recipe

```bash
gcc -O0 -g0 -fno-stack-protector -fno-pie -no-pie -fno-builtin \
    -m64 -Wall -Wextra -Wl,-z,noexecstack -Wl,--build-id=none \
    -o vuln.elf vuln.c
```

Record in `manifest.json`:

- `gcc --version`, `ld --version`, `uname -a`;
- the exact command line;
- `sha256(vuln.c)` and `sha256(vuln.elf)`;
- `readelf -h` type/arch/entry, `readelf -l` load segments and flags;
- symbol addresses for `handle`, `main`, `strcpy@plt`, `puts@plt`;
- the `handle` prologue (`sub rsp, N`) and the buffer offset;
- whether symbols are present (v1: yes; stripping is a later variant).

Constraints:

- **Non-PIE** (`EXEC`), so code addresses are stable and a 5-byte relative call
  can reach the cave.
- **No stack protector**, so the PoC reaches the saved return address instead of
  aborting in `__stack_chk_fail`. This is a teaching fixture, and the manifest
  says so; the vulnerability is the unbounded copy, not the missing canary.
- **No new imports**: the repair uses raw `write`/`exit_group` syscalls, not new
  PLT entries.
- The binary is committed; the source is committed but quarantined by policy and
  by a test (section 9).

### 1.3 ELF facts the analysis must recover

| Fact | Source | Used by |
|---|---|---|
| `ET_EXEC`, x86-64, little-endian, entry | ELF header | analysis, manifest |
| R-X `PT_LOAD` covering `.text` | program headers | cave finder |
| `handle` address and size | `.symtab` | analysis, disassembly slice |
| `handle` frame size (`sub rsp, N`) | disassembly | buffer offset, PoC |
| `call strcpy@plt` address and 5-byte encoding | disassembly | patch site |
| `strcpy@plt` target | `.plt` / relocations | valid-path tail call |
| tail padding after `.text` within the R-X segment | sections/segments | cave candidate |
| no W+X segment, no text relocation | program headers | structure check |

If the compiler emits a different frame (for example, `buf` at `rbp-0x30`), the
manifest records the actual value. Do not hardcode `rbp-0x20`; it is an example,
not a contract.

## 2. Contract: independent expectations

The contract is written by M1, reviewed by M3, and frozen at G1 **before** the AI
audit. It is not generated by the model. It separates stated criteria from
diagnostic hypotheses, following the reference report.

```json
{
  "schema_version": 1,
  "fixture_id": "stack-overflow-01",
  "target_function": "handle",
  "stated_criteria": {
    "capacity_bytes": 32,
    "capacity_includes_terminator": true,
    "max_valid_input_bytes": 31,
    "valid_domain": "printable ASCII, length 0..31, no NUL",
    "valid_behavior": "write the input followed by a single LF to stdout; exit 0",
    "forbidden_behavior": "any write past buf[31], including the terminating NUL",
    "invalid_response": "write exactly the bytes of invalid_stderr to fd 2; exit 1; write nothing to stdout; do not crash",
    "invalid_stderr": "ERROR: input exceeds destination capacity\n"
  },
  "diagnostic_hypothesis": {
    "statement": "handle copies argv[1] into a 32-byte stack buffer with an unbounded strcpy, so inputs of 32 bytes or more overwrite the saved frame",
    "status": "to_be_confirmed_by_analysis",
    "note": "A hypothesis, not an acceptance criterion. The AI may confirm or refute it."
  },
  "allowed_edits": {
    "redirect": "one 5-byte relative call at the strcpy call site",
    "added_code": "at most 256 bytes in the existing R-X segment's verified-unused tail",
    "added_data": "at most 64 bytes in the same R-X segment, RIP-relative references only",
    "forbidden": [
      "new segment",
      "new dynamic import or PLT/GOT entry",
      "text relocation",
      "W+X permission",
      "change to the entry point or the original function's return value on the valid path"
    ]
  },
  "environment_assumptions": [
    "Linux x86-64, non-PIE",
    "glibc with strcpy/puts PLT stubs",
    "no CET shadow-stack enforcement",
    "guest runs with no network and no credentials"
  ]
}
```

The invalid stderr line is a **stated criterion**, so the verifier compares exact
bytes. The diagnostic hypothesis is optional context for the model; a plan that
refutes it with better evidence is acceptable if it still satisfies the stated
criteria.

## 3. PoC and the correct inputs

### 3.1 PoC

| Field | Value |
|---|---|
| ID | `poc-64` |
| Input | 64 bytes of `A` (`0x41`), passed as `argv[1]` |
| Original expected | process terminates by `SIGSEGV` (return code -11 / shell 139); stdout is not asserted because the crash may lose buffered output |
| Candidate expected | exit 1, exact stderr line, empty stdout, no signal |

The 64-byte length overwrites the 32-byte buffer, the saved `rbp` and the saved
return address with `0x4141414141414141`. The exact offset to the saved return
address is derived from the prologue and recorded in the manifest; 40 is the
expected value for the example frame, and the guest run confirms it.

### 3.2 Valid corpus (the "correct input")

| ID | Input | Expected on original and candidate |
|---|---|---|
| `valid-0` | empty string | stdout `\n`, exit 0 |
| `valid-1` | `A` | stdout `A\n`, exit 0 |
| `valid-5` | `hello` | stdout `hello\n`, exit 0 |
| `valid-31` | 31 x `A` | stdout 31 x `A` + `\n`, exit 0 |
| `valid-punct` | `a-b_c.9` | stdout `a-b_c.9\n`, exit 0 |

The 31-byte case is the critical boundary: the NUL goes at `buf[31]`, which is
inside the buffer. A repair that rejects 31 bytes is wrong even though it stops
the crash.

### 3.3 Invalid corpus

| ID | Input | Expected on original | Expected on candidate |
|---|---|---|---|
| `invalid-32` | 32 x `A` | crash or undefined; record actual | exit 1, stderr, no stdout |
| `invalid-33` | 33 x `A` | crash or undefined; record actual | exit 1, stderr, no stdout |
| `invalid-64` | same as PoC | `SIGSEGV` | exit 1, stderr, no stdout |
| `invalid-128` | 128 x `A` | `SIGSEGV` | exit 1, stderr, no stdout |

`invalid-32` is the off-by-one boundary: `strcpy` writes 33 bytes including the
NUL, so the original overflows by one byte. Its actual behavior may be a crash or
a silent corruption; the original observation records what happened. The candidate
must reject it deterministically.

### 3.4 Case file format

```json
{
  "schema_version": 1,
  "fixture_id": "stack-overflow-01",
  "cases": [
    {
      "id": "valid-31",
      "kind": "valid",
      "argv": ["AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"],
      "stdin": "",
      "expected_original": {"exit_code": 0, "stdout": "AAAA...\n", "stderr": ""},
      "expected_candidate": {"exit_code": 0, "stdout": "AAAA...\n", "stderr": ""}
    },
    {
      "id": "invalid-64",
      "kind": "invalid",
      "argv": ["AAAA...64..."],
      "stdin": "",
      "expected_original": {"signal": "SIGSEGV"},
      "expected_candidate": {
        "exit_code": 1,
        "stdout": "",
        "stderr": "ERROR: input exceeds destination capacity\n"
      }
    }
  ]
}
```

Rules:

- Inputs are byte strings, not shell strings. The runner uses `execve` with an
  argv array; it never builds a shell command.
- `expected_original` for a crashing case may be a signal, not an exit code.
- The corpus is frozen at G1. Changing a case after the AI audit requires a new
  fixture version and a new gate.
- The AI sees the PoC input and its observed output (they are given inputs), but
  not the valid/invalid corpus. This keeps the audit from overfitting to the
  verifier.

## 4. Observation format

`guest/run_cases.py` produces one JSON file per binary:

```json
{
  "schema_version": 1,
  "binary": {"path": "candidate.elf", "sha256": "..."},
  "environment": {"uname": "...", "kernel": "...", "libc": "..."},
  "started_at": "2026-12-09T10:00:00Z",
  "cases": [
    {
      "id": "valid-31",
      "argv_sha256": "...",
      "exit_code": 0,
      "signal": null,
      "stdout_b64": "QUFB...",
      "stderr_b64": "",
      "duration_ms": 4,
      "timed_out": false
    }
  ]
}
```

- Bytes are base64 so the evidence is exact.
- A timeout is `timed_out: true`, never a pass.
- A signal is recorded as `SIGSEGV`, `SIGABRT`, etc., plus the raw return code.
- The runner exits 0 only if it collected every case; the verdict is a separate
  computation.
- The guest images reset between original and candidate runs. The original binary
  is read-only and hashed before and after.

## 5. Disassembly view

`pipeline/analyze/` turns the ELF into a `DisassemblyViewV1`:

```json
{
  "schema_version": 1,
  "elf": {
    "sha256": "...",
    "class": "ELF64",
    "machine": "x86-64",
    "type": "ET_EXEC",
    "entry": "0x401120",
    "pie": false
  },
  "segments": [
    {"type": "PT_LOAD", "vaddr": "0x401000", "filesz": 4096, "memsz": 4096, "flags": "R-X"}
  ],
  "symbols": {
    "handle": "0x4011a0",
    "main": "0x4011c0",
    "strcpy@plt": "0x401030",
    "puts@plt": "0x401040"
  },
  "instructions": [
    {"address": "0x4011a0", "bytes": "55", "mnemonic": "push", "op_str": "rbp"},
    {"address": "0x4011a7", "bytes": "e8 84 fe ff ff", "mnemonic": "call", "op_str": "0x401030 <strcpy@plt>"}
  ],
  "plt": {"strcpy": "0x401030", "puts": "0x401040"},
  "sections": [{"name": ".text", "vaddr": "0x401000", "size": 466, "flags": "AX"}]
}
```

Implementation notes:

- Use `pyelftools` for headers, sections, symbols, relocations.
- Use `capstone` for decoding; set `CS_ARCH_X86`, `CS_MODE_64`, `CS_OPT_DETAIL`.
- Slice from the `handle` symbol to the next symbol or the first `ret` that ends
  the function; include `main` and the PLT stubs the function calls.
- Keep the raw bytes for each instruction; the patch site needs them.
- The view contains no source path, no DWARF line table, no source text. A unit
  test asserts the serialized view has no `.c` path and no source lines.
- If `capstone` is unavailable, fail with `error`, do not fall back to a
  hand-written decoder.

## 6. AI repair-plan audit

### 6.1 What the model sees

Allowed:

- the plain-language defect description (one paragraph, no source);
- the PoC input and its observed output;
- `contract.stated_criteria` and `contract.allowed_edits`;
- `contract.diagnostic_hypothesis` (marked as a hypothesis);
- the `DisassemblyViewV1` for `handle`, `main`, and the PLT stubs;
- the output schema and the rule that it must not claim execution.

Not allowed:

- the C source, source path, DWARF line info, build directory;
- the valid/invalid corpus (the model sees only the PoC);
- the reference fix, the verifier code, earlier model outputs;
- any client binary, key, log or unrelated job.

### 6.2 Provider and run set

- DeepSeek chat completions, JSON mode, temperature 0.
- Model id recorded from the provider response; never hardcoded in the report.
- 3 independent runs with the same prompt and input; no cherry-picking. If a run
  is invalid JSON or times out, it stays in the table as a failure.
- Prompt hash and response hash recorded for each run.
- Token usage and estimated cost recorded if the provider reports them.
- No key in the prompt, logs, report or repository.

### 6.3 Prompt shape

System:

```text
You are a binary security analyst. You receive a disassembly view, a defect
description, a proof-of-concept input with its observed output, and independently
stated acceptance criteria. Propose a repair plan as JSON matching the schema.

Rules:
- You see no source code. Do not ask for it and do not invent it.
- Do not claim the binary was executed, tested or fixed.
- Do not invent addresses, instructions or bytes that are not in the view.
- Every edit must be within the allowed edit scope.
- If a criterion cannot be met, say so in "uncertainties" instead of guessing.
- The plan is a proposal; a human reviews it and a deterministic verifier decides.
```

User: the contract JSON, the defect description, the PoC record, the disassembly
view, and the `FixPlanV1` schema. Keep the output schema out of the system prompt
so it can be updated without changing the role text.

The model may give assembly or pseudo-assembly for the stub. Exact byte encoding
is not required at G2; implementability is judged by M5.

### 6.5 Scoring rubric

Two reviewers score independently: M1 (contract/evidence) and M5
(implementability). M3 is consulted on the corpus but does not score. Record both
scores and the resolved score.

| Criterion | Points | What earns it |
|---|---|---|
| Correct diagnosis site | 20 | names the real `call strcpy@plt` address/instruction; no invented address |
| Root cause | 15 | unbounded copy into a 32-byte stack buffer; not "missing canary" or "stack protector" |
| Valid-path preservation | 20 | 0..31 bytes unchanged, including the 31-byte boundary; correct return path |
| Invalid-path contract | 15 | exact stderr, exit 1, no stdout, no crash for 32+ |
| Implementability | 15 | within 5-byte redirect + cave; real PLT target; no new import/segment; reachable |
| Verification proposal | 10 | PoC, 31/32 boundary, regression cases; no claim of execution |
| Honesty and uncertainty | 5 | marks assumptions; no "fixed/tested" claim; says what it cannot know |

Pass: **>= 80** and **no critical error**. Critical errors:

- wrong function/address, or a byte sequence that cannot exist in the binary;
- an edit outside the allowed scope (new segment, new import, W+X);
- a claim that the patch was tested or that the binary is secure;
- a plan that ignores the invalid-path criterion (for example `strncpy` without
  rejection).

Record separately:

- **usable artifact**: schema-valid and M5 says it can be implemented;
- **correctness established**: the plan covers every stated criterion and the
  proposed verification would distinguish fixed from broken.

This separation is the report's recommendation 04. A plan can be usable but not
establish correctness; that is a verification finding, not a model failure.

Raw responses are stored under `docs/audit/raw/` with the key removed and the
response hash recorded. If the raw response contains prompt-injection text, it is
quoted as data, never followed.

### 6.7 Gate decision

- **`proceed`**: at least one plan scores >= 80 with no critical error, and M5
  confirms it is implementable. M1 signs; P3 starts.
- **`iterate`**: best plan is 60-79 or has one fixable defect. Revise the prompt
  or context, rerun up to 3 rounds. The contract, corpus and rubric stay fixed;
  record every prompt change and hash.
- **`change_scope`**: no usable plan after 3 rounds. The product becomes
  "AI-assisted analysis with a human-authored patch"; the report says so. Do not
  lower the rubric or hide the failure.

## 7. Repair plan for P3 (context for the audit)

The expected plan is a trampoline guard, but the audit is open to a better plan
that satisfies the criteria.

```asm
; cave: entered by a 5-byte call replacing "call strcpy@plt"
; rdi = dest (buf), rsi = src (argv[1])
    mov  rdx, rsi
    xor  eax, eax
.len:
    cmp  byte ptr [rdx+rax], 0
    je   .len_done
    inc  rax
    jmp  .len
.len_done:
    cmp  rax, 31
    ja   .too_long
    jmp  strcpy@plt          ; tail call: same return address as the original call
.too_long:
    mov  eax, 1              ; write
    mov  edi, 2
    lea  rsi, [rip+msg]
    mov  edx, MSG_LEN
    syscall
    mov  eax, 231            ; exit_group
    mov  edi, 1
    syscall
msg: "ERROR: input exceeds destination capacity\n"
```

Why it works:

- The stub does not call anything before the tail jump, so stack alignment is
  unchanged and `strcpy` sees the same stack as a direct call.
- `rdi`/`rsi` are preserved for the valid path; `rax` returns `dest` as `strcpy`
  would.
- The invalid path never returns, so `puts` does not run and stdout stays empty.
- Raw syscalls avoid new PLT/GOT entries.
- The cave must be in the R-X segment within rel32 range; the manifest records
  the chosen tail and the original bytes.

The patch is:

- one 5-byte `call` at the `strcpy@plt` site, new displacement to the cave;
- the cave bytes appended into the verified-unused tail of the R-X segment;
- the segment's `p_filesz`/`p_memsz` extended only if the existing file does not
  already contain the tail bytes;
- no change to the entry point, no new segment, no permission change.

M5 may choose a different implementation if the audit plan is better and passes
the same structural checks. The manifest must justify every byte.

## 8. Verification ladder for MVP2

| Check | What it proves | Required |
|---|---|---|
| V0 identity | original and candidate hashes match the manifest; source hash matches; no source in the analysis inputs | yes |
| V1 structure | ELF still valid; same arch/entry; only manifest edits; no W+X; no new imports; cave within the R-X segment | yes |
| V2 valid behavior | every valid case has identical stdout/exit code on original and candidate | yes |
| V3 invalid behavior | every invalid case on the candidate: exact stderr, exit 1, empty stdout, no signal; PoC no longer crashes | yes |
| V4 boundary | 31 accepted, 32 rejected; the guard checks length before `strcpy`, so no write past `buf[31]` can occur; record the static check and the 32-byte rejection | yes |
| V5 reproducibility | re-apply the manifest to the original and get the same candidate hash | optional for MVP2 |

Verdict:

- `verified_against_stated_criteria` only if V0-V4 pass on matching hashes.
- `rejected` if any required check fails.
- `unverified` if the guest is unavailable or a check did not run.
- `unsupported` if the fixture or architecture is outside scope.
- `error` if a tool fails.

No symbolic execution and no formal proof in MVP2. The report's `unverified`
state is a first-class result, not a failure to hide.

## 9. Source-separation tests

These are mandatory and belong to M3/M4:

1. `pipeline/analyze` has no code path that opens `fixtures/**/build/**`.
2. The serialized `DisassemblyViewV1` contains no `.c` path, no `#include`, no
   source line, no DWARF file name.
3. The prompt builder accepts only `DisassemblyViewV1` and `ContractV1`; it does
   not accept a path or a free-form string that could carry source.
4. A test feeds a fake source path into the view and asserts the prompt rejects
   it.
5. The audit report and raw responses contain no `DEEPSEEK_API_KEY`, no
   `Authorization` header and no source text.

## 10. What "correct input" means in the report and in the GUI

The valid corpus is the **correct input** set. It is not "whatever the original
does"; it is the behavior the contract states, checked against the original before
the repair. The GUI shows:

- the case input (escaped), expected output, original result, candidate result,
  and one of `fixed`, `regressed`, `unchanged`, `still_broken`, `not_run`;
- the 31/32 boundary explicitly;
- the verdict banner only from `verdict.json`;
- the uncertainty note: "verified against the stated criteria; not a proof of
  general correctness".

The comparison table is evidence, not the verdict. The match rate, if shown, is
labelled "sample cases matching stated criteria", never "security score".
