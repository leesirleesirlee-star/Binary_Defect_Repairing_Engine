### 2.5 Model-call boundary: why repair execution does not call a model

This is deliberate, not a missing wire. The model boundary is:

| Step | Mode A: signed replay | Mode B: live AI chain |
|---|---|---|
| audit | no call; `skipped(satisfied_by_signed_g2)` | **API host** runs three audit children; model called there |
| decision | no call; human selects the signed decision | no call; human selects one live plan |
| repair | no call; `apply_fixplan` applies the frozen plan | no call; `apply_fixplan` applies the selected plan |
| verify | no call; deterministic verifier | no call; deterministic verifier |
| assistant follow-up | model may be called for the chat reply | model may be called for the chat reply |

The runner never reads a provider key and never calls a model. In Mode A the
three-run AI audit happened at G2 and was signed; G4 replays that evidence. In
Mode B the only model call is the **audit** leg in the API host; the selected
plan is applied by the deterministic repair CLI, and the verifier still writes
the only verdict. The assistant's free-form reply is chat text, not evidence,
and never writes the contract or verdict.

Why:

- **Reproducibility:** replaying the frozen plan keeps the candidate and verdict
  hashes stable; re-asking the model during repair would make the same demo
  produce different bytes.
- **Audit boundary:** G2 is AI proposal + human approval + frozen evidence; the
  execution path must not silently re-generate that evidence.
- **Key boundary:** the provider key stays in the API host; the runner, guest and
  verifier do not receive it.
- **Honesty:** AI output is a clue, not a fact; only the deterministic verifier
  may write `verified_against_stated_criteria`.

## 3. Not run (honest)

- **The continuous live console demo.** No single session was captured that runs
  live audit -> human selects a **live** plan -> repair applies it -> live WSL2
  guest -> verifier verdict. The pieces above were verified separately. **The
  on-site demo is M3's real-machine run** (WSL2 + Ubuntu + the configured key on
  M3's host); this verification host has no key and no WSL2 and cannot stand in
  for it. M2's real audit run (2.1) is implementation evidence only.
- **Applying a live plan is not exercised end-to-end.** M5's
  `tests/repair` live-style plan test (#66) is still open, so the "select a live
  plan and apply it" leg is unproven beyond the audit/select UI.
- **The live audit fans out three concurrent `--runs 1` CLI calls**, not the G2
  harness's sequential loop. Each run uses the same frozen prompt/harness and is
  independent, but the demo record should not imply the exact G2 loop.
- **WSL2 shares the host network**; it is weaker isolation than a disposable VM
  (carried from G3 and #72).

## 4. Demo script

### Mode A — signed replay (default, offline) — ready today

1. `python -m uvicorn app.main:app --host 127.0.0.1 --port 8124`
2. open `/welcome` -> conversation; upload the frozen fixture + cases (or the
   one-click demo).
3. Select contract A; the runner applies the signed G2 plan and verifies against
   M3's recorded observations.
4. Expected: header `7 / 8`, `审计 已跳过 · satisfied_by_signed_g2`,
   `verified_against_stated_criteria`, the three downloads. No key, no WSL, no
   network.

### Mode B — live AI chain (M3's real machine, key + WSL2) — implementation merged, capture pending

1. Save a DeepSeek key in Settings (host-only; `var/assistant.key`) and test the
   connection; ensure WSL2 + Ubuntu are available on the same host.
2. Upload the frozen fixture + cases; choose **AI 现场审计**; wait for 3/3 run
   cards (~1-5 min).
3. Select one of the three live plans (canonical hash shown); confirm the
   live-guest toggle; start.
4. The runner applies the selected plan and runs `guest/live_guest.py`; the
   verifier writes the verdict.
5. Expected if the plan is within `allowed_edits` and V4 recognises its layout:
   a verdict from the verifier; otherwise `unverified` (honest).

Fallbacks — never silent:

| Condition | UI | Runner |
|---|---|---|
| no key | `audit_no_provider`, deterministic replay offered | — |
| audit child fails/times out | `audit_failed`/`audit_summary_invalid` | `live_audit_missing/failed` |
| no WSL2/distro | live-guest badge | `guest_unavailable` |
| guest timeout | — | `guest_timeout` |
| observation hash mismatch | — | `observations_candidate_mismatch` |
| live plan outside allowed edits | selection refused | — |
| model drift changes the plan | three new plans; select one; unrecognised layout -> `unverified` | — |

### Mode C — recorded fallback (demo day)

If the demo host lacks a key/WSL2, play Mode A live and show the screenshots from
2.1/2.2, labelled as recorded evidence. Do not present a recorded run as live.
