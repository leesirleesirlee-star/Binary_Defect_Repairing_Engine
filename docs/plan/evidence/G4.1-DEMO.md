### 2.5 Model-call boundary: why repair execution does not call a model

This is deliberate, not a missing wire. The model boundary is:

| Step | Mode A: signed replay | Mode B: live AI chain |
|---|---|---|
| audit | no call; `skipped(satisfied_by_signed_g2)` | **API host** runs three audit children; model called there |
| decision | no call; human selects the signed decision | no call; human selects one live plan |
| repair | no call; `apply_fixplan` applies the frozen plan | no call; `apply_fixplan` applies the selected plan |
| verify | no call; deterministic verifier | no call; deterministic verifier |
| assistant follow-up | model may be called for the chat reply | model may be called for the chat reply |

The runner never reads a provider key and never calls a model. In Mode A the
three-run AI audit happened at G2 and was signed; G4 replays that evidence. In
Mode B the only model call is the **audit** leg in the API host; the selected
plan is applied by the deterministic repair CLI, and the verifier still writes
the only verdict. The assistant's free-form reply is chat text, not evidence,
and never writes the contract or verdict.

Why:

- **Reproducibility:** replaying the frozen plan keeps the candidate and verdict
  hashes stable; re-asking the model during repair would make the same demo
  produce different bytes.
- **Audit boundary:** G2 is AI proposal + human approval + frozen evidence; the
  execution path must not silently re-generate that evidence.
- **Key boundary:** the provider key stays in the API host; the runner, guest and
  verifier do not receive it.
- **Honesty:** AI output is a clue, not a fact; only the deterministic verifier
  may write `verified_against_stated_criteria`.

### 2.6 Why the console looked instant and model-free (diagnosed 2026-11-24)

The first on-site demonstration reported "no AI repair, cannot call WSL". The root
cause for the first half is design, not a missing wire: the **signed G2 replay** is
deterministic end to end — the three-run audit was signed at G2, the selected plan
is applied by `apply_fixplan`, and verification uses M3's recorded guest
observations. Picking signed Plan A therefore produced a verdict in about a second
with **no model call and no WSL**. Before #81 the signed plans were offered
immediately, so a user could see the whole demo without ever entering the live
agent path or invoking the guest.

The current UI (after #83, merged `5762789`) shows the signed plans by default
after analysis again, with the explicit no-model note; **AI 现场审计** hides the
signed plans, runs the real three-run audit and shows only the fresh audit plan
cards. A presenter who wants the live chain must click **AI 现场审计** explicitly —
picking a signed plan is the ~1 s deterministic replay by design. #81's temporary
explicit choose-gate was superseded by this note plus #83's clearer mode card for
usability; the honesty comes from the note, not from hiding the signed path.

The live guest (`guest/live_guest.py`) is invoked only when the task is in live
mode with `live_guest=true`, and then the runner uses the fresh WSL2 observations.
With the toggle off (or unavailable on a non-Windows host) the runner verifies the
selected plan's candidate against the **persisted recorded observations**; a pass
is possible only if the candidate hash matches the recorded one, and the UI labels
the live guest as unavailable rather than claiming a live check.

So "no AI background repair" was the signed replay being selected, not a missing
model call; "cannot call WSL" is either the same (the signed path never calls the
guest) or a live-path environment issue (Windows host, exact distro name, server
restarted — sections 4 and 5).

### 2.7 M2's macOS full-flow run — the #67 demo evidence (2026-11-24)

M2 exercised the designed AI chain on macOS with a real provider key. macOS cannot
host the WSL2 driver, so the guest leg is the only one not run. **The lead accepted
this run as the #67 demonstration in place of the earlier M3 real-machine
capture**; it is an operator report plus the merged code/tests, not a hash-bound
live-guest run (see the limitation in section 3).

- **Live audit**: the "0/3 for the whole audit" defect is fixed in #83 — the fanout
  writes each finished run into `live_audit.runs`, so the card advances 1/3, 2/3,
  3/3 while the children run; a real run completed with three schema-valid plans.
- **Plan choice**: plans outside the frozen edit budget are marked
  `selectable=false` with a `select_reason` (e.g. run 1's `guard_stub`); they are
  not offered, and the backend still rejects them with `plan_not_allowed`.
- **Repair + verify**: a selectable live plan was applied by the deterministic
  repair CLI, and with the live guest off the runner completed verify and export
  against the persisted observations, producing a `VerdictV1` (not a live-guest
  pass).
- **Guest**: enabling the live guest on macOS returns 409 `guest_unavailable`; the
  toggle is disabled and explained instead of failing mid-run.

The earlier M3 live-guest capture is **no longer required for #67** after this
substitution. Capturing the same flow on a Windows + WSL2 host with the live guest
**on** would upgrade the demo from recorded-observation verification to a fresh
guest check; that remains an optional improvement, not a gate item.

## 3. Not run (honest)

- **The live-guest leg.** No live WSL2 guest run is captured for the demo: M2's
  macOS host cannot run the driver, and the earlier M3 capture was superseded by
  the lead's decision to accept 2.7 as the #67 demonstration. The guest path
  itself is verified by M3's driver run (#72) and the runner's fake-driver tests;
  the 2.7 verdict is based on the persisted recorded observations, **not** on
  fresh guest observations.
- **Live-plan application has end-to-end UX evidence, not a unit test yet.** M2's
  run applied a selectable live plan through the deterministic repair CLI and
  completed verify/export with the guest off; M5's live-style plan test (#66) is
  still open, so the repair unit coverage of a live plan remains pending.
- **Scope enforcement lives in the selection/API layer, not in the apply CLI.**
  The API marks plans outside `allowed_edits` unselectable and rejects them with
  `plan_not_allowed`, but the plan-driven `apply_fixplan` CLI does not
  independently re-check the contract budget (M5 reproduced a valid `FixPlanV1`
  with 257-byte code that the CLI accepted). The demo's scope safety therefore
  rests on the selection/approval gate and the human choice; #66 covers the
  positive live-style apply and does not turn the CLI into a contract-aware
  validator.
- **The live audit fans out three concurrent `--runs 1` CLI calls**, not the G2
  harness's sequential loop. Each run uses the same frozen prompt/harness and is
  independent, but the demo record should not imply the exact G2 loop.
- **WSL2 shares the host network**; it is weaker isolation than a disposable VM
  (carried from G3 and #72).

## 4. Demo script

### Mode A — signed replay (default, offline) — ready today

1. `python -m uvicorn app.main:app --host 127.0.0.1 --port 8124`
2. open `/welcome` -> conversation; upload the frozen fixture + cases (or the
   one-click demo).
3. Select contract A; the runner applies the signed G2 plan and verifies against
   M3's recorded observations.
4. Expected: header `7 / 8`, `审计 已跳过 · satisfied_by_signed_g2`,
   `verified_against_stated_criteria`, the three downloads. No key, no WSL, no
   network.

### Mode B — live AI chain (optional live-guest capture; not required for #67)

1. Run the console on **Windows** (PowerShell), not inside the WSL distro: the
   live-guests stage calls `wsl.exe`, and the path mapper only understands
   `D:\...` host paths. The distro name must match the driver's default
   (`Ubuntu`) or `BINARYREPAIR_WSL_DISTRO` must be set to the exact `wsl -l -q`
   name **in the server's environment before it starts** (the runner inherits it;
   it does not pass `--distro` itself).
2. Save a DeepSeek key in Settings (host-only; `var/assistant.key`) and test the
   connection.
3. Upload the binary first (the sequential flow probes it), then the case files;
   or use the one-click demo. **Signed plans are visible by default after
   analysis** — click **AI 现场审计** explicitly so the console hides them and runs
   the real three-run audit; wait for 3/3 run cards (~1–5 min).
4. Select one of the selectable live plans (canonical hash shown; plans outside the
   frozen edit budget are not offered), enable the **live guest** toggle, start.
5. The runner applies the selected plan and runs `guest/live_guest.py`; the
   verifier writes the verdict from the fresh WSL2 observations.
6. Expected if the plan is within `allowed_edits` and V4 recognises its layout:
   a verdict from the verifier; otherwise `unverified` (honest). With the live
   guest off, verification uses the persisted recorded observations and is not a
   live-guest check.

Fallbacks — never silent:

| Condition | UI | Runner |
|---|---|---|
| no key | `audit_no_provider`, deterministic replay offered | — |
| audit child fails/times out | `audit_failed`/`audit_summary_invalid` | `live_audit_missing/failed` |
| no WSL2/distro | live-guest toggle disabled/explained or badge | `guest_unavailable`; with guest off, verify uses recorded observations (pass only on hash match) |
| guest timeout | — | `guest_timeout` |
| observation hash mismatch | — | `observations_candidate_mismatch` |
| live plan outside allowed edits | selection refused (`plan_not_allowed`) | apply CLI is plan-driven; enforcement is at the selection layer (section 3) |
| model drift changes the plan | three new plans; select one; unrecognised layout -> `unverified` | — |

### Mode C — recorded fallback (demo day)

If the demo host lacks a key/WSL2, play Mode A live and show the screenshots from
2.1/2.2 plus M2's macOS full-flow run (2.7), labelled as recorded evidence and with
the live guest marked off. Do not present a recorded run or a guest-off verify as a
live-guest check.

## 5. Optional: upgrade the demo to a fresh live-guest check (not required for #67)

The #67 demo is closed on M2's macOS run (2.7). This checklist only upgrades it
from recorded-observation verification to a fresh WSL2 guest check.

1. On **M3's demo host**: Windows console (not inside WSL), `wsl.exe -l -q`
   shows the distro name, and the server was started after `git pull` with
   `BINARYREPAIR_WSL_DISTRO=<exact name>` if it is not `Ubuntu`. Verify directly:
   `wsl.exe -d <name> -e uname -a` and
   `python guest/live_guest.py --original fixtures/stack-overflow-01/vuln.elf
   --candidate <candidate.elf> --cases fixtures/stack-overflow-01/cases/cases.json
   --out-dir var/live-guest-check`.
2. Fresh boot the guest: `wsl --terminate <name>`.
3. Start the console (a **new** uvicorn process on the current checkout, not a
   stale one on port 8124), save/test the key, run Mode B with the **live guest
   toggle on**, keep the browser open until the terminal state.
4. Save: the audit summary + the three plan hashes, the selected plan's
   canonical hash, `candidate.elf` hash, the live observation hash + environment,
   the persisted verdict hash, and screenshots of the three plan cards and the
   verdict.
5. Update this file: replace `not_run` with the commands, hashes and screenshots;
   note the model, duration and any fallback that occurred.
6. If a live plan is unrecognised by V4, record `unverified` and do not claim
   success.

## 6. Scope and non-claims

- The AI proposes; the human selects; the verifier alone decides. The assistant
  and the live audit never write the contract or the verdict.
- The claim remains `verified_against_stated_criteria`, scoped to the frozen
  contract/corpus; never "secure" or "correct in general".
- `apply_fixplan` is plan-driven: the frozen edit budget is enforced by the
  selection/API layer, not by the repair CLI (M5 review, #66 scope).
- G4 stays signed; this record is additive and does not change
  `docs/plan/evidence/G4-RECORD.md`.
